# DashBooking Salon Owner Landing Page Design

**Date:** 2026-04-28  
**Status:** Draft for review  
**Goal:** Define the approved design direction for a premium, multilingual DashBooking landing page that converts salon owners through a primary lead form while showcasing the real product scope.

## 1. Product and conversion objective

This page is for nail and beauty salon owners who want more bookings, less front-desk stress, and a system that is easy to understand quickly.

The page must answer five questions fast:
1. Can this help me get more bookings?
2. Will it reduce missed calls and front-desk pressure?
3. Is it practical for daily salon use?
4. Does it support Clover and Poynt workflows?
5. How do I contact the team and get started?

**Primary conversion:** lead form submission.  
**Primary CTA behavior:** hero CTA scrolls to the lead form.  
**Secondary trust supports:** visible pricing, visible phone/contact path, proof sections, FAQ.

## 2. Scope model

### Main scope
The landing page must position DashBooking as a salon system focused on:
- Google / online booking demand capture
- AI receptionist call handling
- appointment calendar and daily salon operations
- Clover / Poynt support
- booking-based pricing
- direct lead capture

### Secondary / add-on scope
These stay visible but are not the headline promise:
- website services
- SMS reminders
- deposits
- gift cards
- reviews / replies
- promotional design support

The page should not read like a generic all-in-one platform claim. It should read like a practical salon-growth and front-desk-relief system with operational support.

#### Clean internal competitive map
- **Fixed monthly tier platforms:** BelleBiz, GlossGenius, Boulevard, Mangomint
- **Staff / calendar / team-based platforms:** Fresha, Vagaro, Booksy, Fastboy, Mangomint
- **Location-based platforms:** Square, Boulevard, Mangomint
- **Marketplace-fee platforms:** Fresha Marketplace, Booksy Boost
- **DashBooking lane:** Volume-based booking/POS pricing + AI receptionist + Google Booking + salon operations + optional add-ons

#### Why DashBooking pricing feels different
Most salon software pricing grows in ways that are hard to feel until later:

- **Fixed monthly plans** — you pay every month, even when bookings are slow.
- **Staff or calendar pricing** — the price grows as you add technicians, calendars, or service providers.
- **Location pricing** — some systems charge by salon location.
- **Marketplace fees** — some platforms may charge when they bring you a new client through their marketplace.
- **DashBooking volume-based pricing** — DashBooking ties the core booking/POS system to successful booking volume. If there are no bookings through DashBooking, you pay `$0/month`.

Keep these lines visible in the public landing-page pricing message:
- `$0 if no bookings`
- `No contract`
- `Cancel anytime`
- `Pricing based on booking volume`
- `Walk-ins and manually entered bookings are not charged`

#### Public-facing competitive messaging rule
Use calm pricing-model comparison only.

Preferred public copy:
- `Other platforms often charge fixed monthly fees, per-staff fees, per-location fees, or marketplace commissions. DashBooking is different: your core booking/POS pricing is based on booking volume, so you only scale cost when the system is actually helping bring appointments in.`
- `With many systems, you pay every month whether customers book or not. With DashBooking, if there are no bookings through DashBooking, you pay $0. No contract. Cancel anytime.`

Competitive framing should support three beliefs:
1. I can start without heavy fixed software risk.
2. I can capture more bookings from Google and phone demand.
3. I can run real salon workflows without stitching together multiple systems.

## 7. Multilingual strategy

The page should launch with multi-language support from day one.

### Languages
- Vietnamese (`vi`) — default launch language
- English (`en`)
- French (`fr`)

### Strategy
Use one shared page architecture and one shared visual system, with locale-driven content managed through i18n.

Rules:
- Vietnamese is the default landing-page locale.
- English and French are alternate locales.
- Locale switching should be handled through the app's i18n routing/content layer, not by duplicating page structure.
- Pricing, proof blocks, CTA logic, and form behavior stay structurally identical across locales.

Separate content by language for:
- headlines
- body copy
- bullets
- CTA text
- FAQ
- form labels
- validation copy
- success messages

This avoids design drift between languages and keeps pricing, proof, and form behavior consistent.

## 8. Lead capture system boundary

The form is a real submission system, not just a UI mock.

### Required submission flow
1. user submits form
2. server validates required fields
3. server writes lead into Google Sheets
4. server sends Telegram bot notification
5. server returns success response
6. frontend shows success state
7. analytics hook may fire after success

### Core fields
- name
- salon name
- phone number
- city / province
- preferred language
- what do you need help with?

### Recommended metadata
- page language / active locale
- source
- timestamp
- optional UTM fields

### Security boundary
- Google Sheets credentials stay server-side
- Telegram bot token stays server-side
- no direct client-side integration with Sheets or Telegram

### Anti-spam baseline
- honeypot field
- rate limiting
- minimum submit-time check
- basic phone validation
